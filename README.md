# Работни карти — МиТ / Ар Си Техник

Управление на сервизни заявки, график, механици, работни карти, материали и справки.
Интерфейсът е HTML/CSS/JavaScript. Реалният API е Supabase Edge Function, а данните са в PostgreSQL.

Офисни права: координаторът създава заявки и редактира описанието, данните за клиента/машината и бележките. Назначаването на механици, графикът и приключването чрез работна карта остават за ръководител/управител. Координаторът няма право да изтрива заявки или да редактира карти.

## Локално демо — една команда

Нужен е Node.js 22 или по-нов. За демото няма инсталация на пакети, Docker, Microsoft вход или облачна база.

```powershell
cd "C:\Users\kiril_vasev\OneDrive - Raicommerce\Documents\ChatGPT\Work cards MiT"
node scripts/dev-server.mjs
```

Отвори http://localhost:3000/login.html. Избери роля и влез в демо профила.
„Механик → Демо механик“ има примерна назначена задача. Избери „Поемам задачата“, после „Попълни работна карта“.
При презареждане въведените полета, количествата и текущата стъпка се възстановяват.
За запис попълни и km/м.ч., избери дали има материали и въведи човекочасове.

`npm run dev` прави същото, ако имаш npm. Спиране: Ctrl+C.
Друг порт: `$env:PORT=3001` преди стартиране (само за демо; реалният API и Entra изискват съответния разрешен адрес).

**Демото използва измислени данни в паметта и никога не изпраща заявки към облачния Supabase.**
Данните се нулират при рестарт на сървъра. Локалните чернови остават в браузъра и се разделят по среда, проверена самоличност и заявка.
Демо входът съществува само в локалния Node сървър; Edge Function не приема такъв вход.

## Реален backend за разработка

За отделна локална база: Supabase CLI и Docker. От корена на проекта:

```powershell
supabase start
Copy-Item supabase/functions/.env.example supabase/functions/.env
supabase functions serve api-proxy --env-file supabase/functions/.env
```

Първото `supabase start` прилага миграциите и локалния seed върху новата локална база.
Не използвай `db reset` върху среда с нужни данни. След добавяне на нови миграции към съществуваща локална база използвай `supabase migration up --local`.
В друг терминал:

```powershell
node scripts/dev-server.mjs --backend
```

По подразбиране този режим използва `http://127.0.0.1:54321/functions/v1/api-proxy`.
За друга отделна тестова среда задай `$env:WC_API_URL='https://TEST-PROJECT.supabase.co/functions/v1/api-proxy'`.
При различна Entra регистрация задай `WC_ENTRA_CLIENT_ID`, `WC_ENTRA_TENANT_ID` и `WC_ENTRA_SCOPE`.
Сървърните `WC_ENTRA_CLIENT_ID` и `WC_ENTRA_TENANT_ID` трябва да съвпадат.

Няма автоматичен fallback от реален API към демо данни.
Промените в `--backend` режима се записват в избраната база.

## Microsoft Entra

1. В App registration настрой SPA redirect URI `http://localhost:3000/login.html`; запази и реалния GitHub Pages redirect URI.
2. В **Expose an API** добави delegated scope `api://<CLIENT_ID>/access_as_user` и разреши на SPA да го заявява; при нужда приложи съгласие от администратор.
3. В manifest на API настрой `api.requestedAccessTokenVersion` на `2`.
4. Public настройките са в `app-config.js`. За реална публикация смени тях, ако използваш отделна регистрация.
5. След миграцията свържи всеки офис потребител с неговия **Entra user Object ID** и Tenant ID. Application Object ID и Client ID не са User Object ID.

Пример с placeholders за SQL Editor, след като установиш правилния потребител:

```sql
insert into public.user_roles(email,name,role,microsoft_oid,tenant_id,is_active)
values ('user@example.com','Име на потребителя','admin','USER-OBJECT-ID','TENANT-ID',true)
on conflict(email) do update set
  name=excluded.name,role=excluded.role,microsoft_oid=excluded.microsoft_oid,
  tenant_id=excluded.tenant_id,is_active=true;
```

Имейлът е за показване и администрация. Достъпът се определя от подписания `oid` + `tid` и активната роля в базата.
Graph токени с `User.Read`, ID токени и роля от sessionStorage не дават достъп до API.
Проверяват се RSA подписът, issuer, audience, tenant, срокът и scope `access_as_user`.

## Таблети

Ръководител или управител влиза в „Устройства“, избира активен механик и издава код.
Кодът се показва само веднъж и се въвежда на таблета в „Механик → Код за регистрация“.
Таблетът получава само задачите и картите на този механик. Свободната карта може да е само от негово име; карта по заявка може да включва назначените съекипници.
В базата се пази SHA-256 отпечатък, а не оригиналният код. Регистрацията е за 90 дни и може да се отпише веднага.
Изходът запазва регистрацията и неизпратените чернови. Отписването се прави от екрана „Устройства“.
Всеки браузърен профил/таблет е за един механик; споделен профил изисква отделна регистрация при смяна на механика.

## Цялостен запис и чернови

`submit_work_card` записва картата, материалите, историята и приключването на заявката в една PostgreSQL транзакция.
При грешка всичко се отменя. Ключът за повторно изпращане се запазва в черновата преди мрежовия опит.
Същият ключ със същите данни връща същата карта. Други данни с вече използван ключ се отхвърлят.
Заключването на заявката не позволява две различни карти едновременно да я приключат.
Редакцията и изтриването на карта също са транзакционни; изтриването отваря свързаната заявка отново.

При неизвестен резултат от мрежов опит полетата се заключват. Натисни отново „Запиши работна карта“: изпращат се същите данни и същият ключ.
При потвърден отказ на API (напр. невалидни данни) полетата се отключват за корекция.
Черновата се изчиства след потвърден успешен запис, никога само защото е натиснат бутонът.
Ако паметта на браузъра е пълна/забранена, има видима грешка и записът не се изпраща без запазен ключ.

Без интернет може да се продължи отворена карта; след поне едно онлайн зареждане PWA кешът и запазените номенклатури позволяват възстановяване и след презареждане в същата сесия.
За изпращане винаги е нужна връзка и валидна сървърна самоличност. Няма автоматично изпращане във фон.
PWA кешира само статичните файлове, не API отговори. CDN шрифтове, Microsoft входът, Excel библиотеката и Chart.js изискват интернет при първо зареждане.

## Прилагане към съществуващия Supabase

Промените в хранилището не променят автоматично работещия сайт или базата.
Baseline схемата е възстановена от кода и е проверена върху нов PostgreSQL. Пълно копие на реалната база не е изтегляно; предоставена е проверка на нейните колони, ограничения и права.

Получената впоследствие проверка на реалната схема потвърждава UUID идентификаторите и text[] масивите, както и задължителното `user_roles.name`.
В нея има и `synced`, `created_at` и допълнителни колони за историята, които не бива да се премахват.
За ръчно изпълнение в SQL Editor първата съвместима стъпка е `supabase/manual/01_prepare_existing.sql`.
Тя добавя само пет nullable колони и запазва текущите права и поведение; не включва новата защита или транзакционния запис.
След потвърждение на петте колони `supabase/manual/02_atomic_submit.sql` инсталира само функцията за цялостен запис и уникалния индекс за повторно изпращане. Запазва правата на съществуващите таблици и отказва да презапише друга функция със същото име. Функцията е подготвена за новия API; старият клиент продължава да използва отделните си заявки до публикуването на новата версия.
`supabase/manual/03_task_and_card_helpers.sql` добавя останалите три функции: започване на задача, транзакционна редакция и транзакционно изтриване на карта с отваряне на заявката отново. Самото инсталиране не изпълнява тези операции и запазва достъпа до таблиците. Изпълнението на новите функции е разрешено само за `service_role`.
`supabase/manual/04_link_office_user.sql` свързва един съществуващ активен офис потребител с проверените му User Object ID и Tenant ID. Замени трите placeholders преди изпълнение. Скриптът запазва ролята и отказва липсващи/неактивни потребители, дублиран имейл с различен регистър, друга съществуваща връзка или самоличност, вече свързана към друг запис. Повтаря се за останалите офис потребители преди включване на новия API. Личните идентификатори не се записват в шаблона в хранилището.
`supabase/manual/05_link_office_users.sql` свързва списък от потребители в една транзакция. Замени Tenant ID и JSON списъка с проверените имейли, Object ID и очаквани съществуващи роли. При конфликт, липсващ профил или промяна на очаквана роля целият списък се отменя. Повторение със същите данни е допустимо; ролите не се променят. Личните идентификатори остават извън шаблона.
`supabase/manual/office_users_pending.sql` показва само активните записи без пълна Microsoft връзка. Провери ги преди включване на новия API, за да не останат служители без достъп.
`supabase/manual/06_prepare_device_registry.sql` подготвя само новата таблица за регистрирани устройства с RLS и права само за `service_role`. Запазва данните и правата на съществуващите таблици и отказва да променя чужда таблица със същото име. Повторното изпълнение запазва регистрациите. Това не защитава стария proxy: издавай кодове едва след обновяване на всички API входове към базата.
Не изпълнявай цялата security миграция като заместител на тази първа стъпка: тя е част от съгласуваното обновяване на клиента, API и Entra.

### Тест на новия API през Dashboard

`supabase/manual/api-proxy-v2.ts` е самостоятелен генериран файл за Supabase Dashboard. Няма външни импорти и съдържа същите проверки като модулния API. Генерира се с `node scripts/build-dashboard-bundle.mjs`; тестът отказва, ако файлът се разминава с изходния код.

В Edge Functions избери **Deploy a new function → Via Editor**, задай ново име **api-proxy-v2** и постави целия файл като `index.ts`. Конфигурирай сървърните `WC_ENTRA_CLIENT_ID`, `WC_ENTRA_TENANT_ID`, `WC_ALLOWED_ORIGINS` и проверката на Microsoft токените от самата функция (Supabase JWT проверката за тази функция е изключена). `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` се осигуряват от Supabase. Стойностите не се публикуват в клиентски файлове.

Тестовият адрес е `https://PROJECT.supabase.co/functions/v1/api-proxy-v2`. За локален Microsoft вход трябва SPA redirect URI `http://localhost:3000/login.html` в съществуващата Entra регистрация. Насочи `WC_API_URL` към тестовия endpoint и стартирай `node scripts/dev-server.mjs --backend`.

Използвай новия endpoint за проверка на своя офис вход преди обновяване на работещия сайт. Старият proxy остава проблем за сигурността, докато приема непроверени заявки: публикуването на защитен v2 endpoint само по себе си не го поправя. При окончателното обновяване замени и кода на стария `api-proxy` със защитения handler, обнови интерфейса, приложи ограниченията за таблиците и регистрирай таблетите. Нови регистрации на устройства се издават след защитата на всички останали API входове към същата база.

Регистрацията на таблетите е отложена по решение на потребителя. Засега офисната част се проверява локално срещу `api-proxy-v2`; не изпълнявай стъпка 06, не издавай кодове и не превключвай целия работещ сайт/API, докато не е съгласуван входът за механиците. Последваща промяна на `api-proxy-v2.ts` се публикува отново в същата тестова функция.

1. Направи backup/schema dump на реалната база. Изпълни `supabase/preflight.sql` в SQL Editor. При разминаване съгласувай типовете и baseline-а със schema dump; не променяй реални типове на сляпо.
2. Приложи двете миграции по ред в тестова среда и провери работния процес. За съществуващи таблици baseline-ът използва `CREATE TABLE IF NOT EXISTS` и не ги пресъздава. Не прилагай `seed.sql` към реалната база.
3. Настрой Entra scope, v2 access tokens и Object ID връзките в `user_roles`.
4. Задай server secrets `WC_ENTRA_TENANT_ID`, `WC_ENTRA_CLIENT_ID`, `WC_ALLOWED_ORIGINS` (включително `https://kirilvassev-jpg.github.io`). Supabase осигурява `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`.
5. В прозорец за обновяване приложи миграциите към реалната база, публикувай Edge Function и после обновените статични файлове. Новият API и старият клиент не са съвместими: старият клиент не изпраща нужните access tokens и не ползва RPC.
6. Регистрирай таблетите и провери всяка роля. При проблем използвай backup и съгласувано връщане на клиент/API/схема; не връщай само стария незащитен proxy.

Миграцията отнема директните права на `anon`/`authenticated` върху таблиците и включва RLS. Новите RPC са достъпни само за `service_role`; Edge Function проверява и ограничава всяка операция преди използването им.
Никога не публикувай service-role ключ. JWT проверката на Supabase gateway е изключена, защото токените са Microsoft, но самата функция винаги ги проверява. Публичната операция `health` връща само `{ok:true}` след заявка без записи.
